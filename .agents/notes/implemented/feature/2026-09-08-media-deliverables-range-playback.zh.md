# Agent Note: 媒体交付物通过 HTTP Range 原生预览播放

Status: implemented

[English](2026-09-08-media-deliverables-range-playback.md) | 中文

## Problem

交付物能读但不能播：协作者录制的屏幕录像或配音在应用内没有预览——文件卡片只提供下载或外部打开。现有的整文件字节通道也不支持 `Range`，即使手写 `<video>` 元素也无法拖动进度：浏览器通过请求字节切片来拖动，而每次都以整个文件应答的服务器会让每次拖动都变成一次完整下载。若为服务媒体而在主机端缓冲整个视频，预览 RPC 和字节通道都要付出与媒体时长成正比的内存代价。

## Decision

视频（`.mp4`、`.m4v`、`.webm`）和音频（`.mp3`、`.wav`、`.ogg`、`.oga`、`.m4a`、`.flac`、`.aac`、`.opus`）交付物通过浏览器原生播放器预览，同时 artifacts 字节通道（`artifacts.raw`）支持单区间 HTTP `Range`：

- 转发的 `Range` 头只接受 `bytes` 单元的单一区间。`bytes=a-b` 通过文件句柄在偏移处读取并应答 206 切片（数 GB 的视频也不会被完整缓冲）；`bytes=a-` 到文件末尾；`bytes=-n` 按文件大小解析为后缀区间；结束位置向文件大小收敛；无法满足的区间以 `416` 和 `bytes */<size>` 应答；畸形或多区间头回退为整文件 `200`，播放器将其视为普通成功。每个应答都带 `Accept-Ranges: bytes`。
- 媒体预览载荷只含标识信息，并在任何字节读取之前短路；播放器走原始字节通道。
- 播放器以路径为 key，切换文件即重建元素，播放状态不会跨文件泄漏。
- `.mov` 刻意不在原生播放集合内：QuickTime 容器在 Chromium 与 Firefox 中无法播放，一个无法播放且没有兜底入口的死播放器不如诚实的路径——`.mov` 文件保留通用预览并用系统播放器打开。

扩展名清单存在于四个必须保持一致的位置——主机端内容类型表、主机端媒体类型判定、以及两个客户端分发器——每处都带有指向其余位置的注释。

## Alternatives considered

- **整文件应答并带 `Accept-Ranges: none`**：改动最小，但拖动进度会重复下载，长录像在面板中不可用；播放本身就是目标，故拒绝。
- **主机端转码为统一格式**：能归一化容器，但会给每个平台包增加媒体工具依赖，并对每次预览施加质量与延迟税；违背"不强制安装任何办公级体积依赖"的规则，拒绝。
- **客户端播放器库**：只有服务端支持 Range 时才能解决拖动问题，而原生元素已能做到，徒增包体；拒绝。
- **为 Safari 用户保留 `.mov` 原生路径**：一个平台获得面板内播放，其余浏览器都会看到没有下载入口的坏播放器；为一致的外部打开体验，拒绝。

## Consequences

媒体预览 RPC 的开销与文件大小无关（O(1)），拖动只花费所请求的切片，播放状态也不会在文件间泄漏。代价是：新增格式时四处扩展名清单必须一起移动；能播放哪些容器由浏览器而非我们的代码决定——Chromium 与 Firefox 无法解码的格式，只有在具备明确兜底方案时才能进入原生集合。
