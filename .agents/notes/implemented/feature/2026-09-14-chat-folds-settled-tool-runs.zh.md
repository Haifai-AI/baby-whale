# Agent Note: Chat folds a settled tool run into one summary line

Status: implemented

[English](2026-09-14-chat-folds-settled-tool-runs.md) | 中文

## Problem

一次调用工具的回合会为每次调用渲染一行，一行接一行，中间散布着正文。在一个真实的 23 步会话上实测，记录区显示了 15 行工具行、占据约 700px 视口中的 332px——将近一半的阅读区域都是过程。更长的回合会把答案完全挤出屏幕。

这些行单独看并没有错；Web 客户端的工具行本身已经是一行安静的单行。问题在于数量和扁平度。每一次调用都以同样的权重渲染，无论它是读取文件还是失败；行与行之间没有间隙，因此读起来像纹理而非列表；工具名在每一行重复（`Bash ·` 出现五次）。记录区无法区分"这是答案"与"这是我为得到答案所做的事"。

显而易见的修法——折叠工具行——有一个值得点明的风险。仅按工具调用的相邻性折叠在这个客户端里行不通：一个回合渲染为 `assistant-step` 与 `tool-call` 交替的 Node，因此最长的连续工具调用通常只有两个。基于该判据构建的折叠在单元测试里看起来正确，在产品里却什么也不会做。这一点在编写分组逻辑之前，通过从实时会话导出 flow kind 序列得到了确认。

## Decision

`ui-conversation` 将 Chat 的流分组为若干"过程"运行段，并把已结束、无失败、长度足够的运行段折叠为一行摘要。

**运行段的边界是正文，而非调用的相邻性。** 运行段是流顺序中一段最大的连续切片，其内的 Node 全部属于过程：工具调用，以及不携带非空文本的 assistant step。携带正文的 step 会终止运行段，因为答案正是折叠要保护的对象。只携带推理的 step 属于过程，会随其周围的调用一同隐去。任何其他 Node 类型——用户消息、命令、压缩标记、回合尾部——都属于内容，同样终止运行段。无法识别的 block 按内容处理，而不是去折叠分组逻辑读不懂的东西。

**折叠是派生的，绝不存储。** `groupToolRuns` 是流顺序与运行时 `ChatNodeStore` 的纯函数，在 `ChatView` 中按两者记忆化。运行段身份取其首个 Node key，因此向进行中的运行段追加调用会保留其折叠状态，而不会重新挂载摘要。

**折叠条件。** `foldsByDefault` 需要同时满足三个条件：运行段已结束、其中没有任何调用失败或中断、且覆盖至少三次工具调用（`MIN_FOLDABLE_RUN`）。这个阈值是刻意的：折叠两行只省下一行，却要付出一次点击。仍在工作的运行段保持行可见，以便持续观察实时调用；失败的运行段同样保持行可见，因为被折叠的失败就是需要用户自己去寻找的失败。

**读者掌控什么。** `ChatStoreState.expandedRuns` 保存读者展开过的运行段 key，且只存储"展开"这一个方向。不满足默认折叠条件的运行段不提供折叠，因此不需要"收起"的另一半；而在运行期间被展开的运行段在结束后依然保持展开，不会在读者眼皮底下重新折叠。

**摘要说什么。** 工具调用的数量（而非覆盖 Node 的数量——两者不同，因为一个运行段也跨越推理 step），以及运行段结束后的墙钟跨度，从首个覆盖 Node 到最后一次结算。任何含有未结算 Node 的运行段都不报告时长，因为部分计时的跨度会为仍在进行的工作打印出一个时长。时间取自与行模型相同的 block 字段，因此摘要不可能与它所替代的行相矛盾。

摘要行的样式是"会响应悬停的弱化文本"，而非带边框或填充的控件：记录区里出现第二种外壳会与输入框争夺注意力，而输入框是那里唯一的另一个控件。它带有说明数量与动作的提示气泡，因此一个没有标签的数字无需点击即可自我解释。

## Alternatives considered

- **仅按连续的工具调用折叠** —— 最直接的判据，也是读者会假设的那一种。在测量真实施流后被否决：assistant step 位于调用之间，运行段几乎永远达不到折叠阈值，功能看起来已实现却毫无效果。
- **折叠整个回合（所有 step 与调用并为一行）。** 这是可获得的最大压缩幅度。被否决，因为它连同答案自身的正文一起隐藏；读者必须展开回合才能读到智能体说了什么。
- **始终折叠推理 step。** 按同样的论证它们属于过程。作为独立决策被否决：推理行承载智能体自述的意图，折叠它们对回合观感的改变远超工具日志的范围。它们仅在位于调用之间时随运行段一并折叠，而这种情况已被运行段边界覆盖。
- **为每个工具引入严重度概念**（常规成功折叠，破坏性操作保持醒目）。本次变更否决：这需要当前渲染意图并不携带的逐工具元数据，而失败与存活状态已经覆盖了读者必须看到行的情形。
- **以两次调用而非三次为阈值折叠。** 被否决：只省下一行，代价是一次点击外加多一个需要扫视的对象。
- **除展开集合外再持久化一个收起集合。** 被否决：不满足默认折叠条件的运行段不提供折叠，因此收起方向只会记录它本已计算出的默认值。
- **复用 assistant node 的 `hasVisibleContent` 来判定过程与内容。** 被否决：该判据把推理计为可见内容，与运行段边界所需的分类恰好相反。

## Consequences

在实测的 23 步会话上，一个已结束回合的流高度从 2746px 降至 1800px——946px、约三分之一的记录区——被四行摘要取代，可见工具行从 15 行降至 5 行。答案现在与其过程并列，而非位于其下。

Chat 与 Trajectory 两个标签页不再互相重复：Trajectory 仍是完整的密集日志，Chat 则成为叙事，这正是它的名称与位置早已暗示的分工。

代价与限制。折叠依赖 Node 类型保持稳定，因此新的 Chat Node 类型默认按内容处理并终止运行段——这是安全的方向，但也意味着未来某个属于*过程*的 Node 类型必须显式加入 `foldNode`，否则会静默地把运行段切成两段。摘要报告的是墙钟跨度而非工具耗时之和，因此存在空闲间隔的运行段会显示比实际工作更长的时长；精确总计仍由输入框下方的统计行负责。`expandedRuns` 以 Node key 为键，因此当会话窗口重新加载并越过某个运行段时，该运行段的展开状态会随 Node 一同丢失。
