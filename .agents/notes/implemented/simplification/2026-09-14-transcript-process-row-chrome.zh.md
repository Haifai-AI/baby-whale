# Agent Note: The transcript's process rows consolidate on one chrome

Status: implemented

[English](2026-09-14-transcript-process-row-chrome.md) | 中文

## Problem

对话记录中每一个表示过程的单元——工具调用、推理块、斜杠命令、注入的上下文、skill 调用——都各自实现了同一种行。这样的实现有七份：`ToolRow`、`ReasoningRow`、`GenericCommandCard`、`ContextInjectionRow`、`SkillRow`、Bash toolview，以及折叠运行的摘要行。其中五份组合了共享的 `DisclosureRow`，两份手写了它的标记。

它们已经漂移成同一个对象的四种互不兼容写法。当某一行组合该外壳时，其说明文字是 13px/22px；当它手写外壳时，则是 14px/24px。动词与其说明之间的分隔符，在一个家族里是 3px 圆点，在另一个家族里是 2px 圆点，并且取自三种不同的 token。最要命的是，[视觉世界那篇 Agent Note](../process/2026-09-14-web-client-apple-visual-world.zh.md) 曾把运行状态记为"一条 1px 移动的强调色细线，取代原先横扫该行自身字形的 300px 眩光带——后者恰好让它本应注释的文字变暗"，而这只对其中一行成立。推理、命令、skill 与 Bash 各行仍在横扫那条眩光带。

结果是这一行完全没有层级。在运行中的应用里实测，工具行以 `label-secondary` 的 14px/400 绘制标题，以 `label-tertiary` 的 13px/400 绘制摘要，中间隔着一个在画布上合成为 **1.98:1** 的 3px 圆点。一像素的字号差加上零字重差，是读者看不出来的区别；而那个圆点低于对比度下限，读起来既不是标点也不是边界。整行读下来是一句灰色的连绵文字；在一个有三十多个推理块的会话里，它是屏幕上重复次数最多的对象。

## Decision

由一套外壳拥有这一行，五种类型之间的差别从结构变为等级。`ui-primitives` 中的 `DisclosureRow`——七份实现里已有五份使用的共享原子——成为唯一定义：24px 行高、`--dsw-alias-fill-l2` 上的 **20px 前置方块**（取 6px 行圆角）、8px 间距、**`label-primary` 的 13px/22px medium** 动词、8px 间距，以及 `label-tertiary` 的 13px/22px 截断说明文字。

方块就是这次的关键动作。它让每一行都有明确的左边缘，使一行读作坐落在文本轴上的一个对象，而不是又一行灰色文字；并且它无需引入任何字形就取代了分隔圆点：动词的 500 相对说明文字的 400 构成完整字重差，而 `label-primary` 相对 `label-tertiary` 相差两级色阶。任何过程行都不再绘制分隔符。两份手写外壳的行——Bash 与 Skill——重复这些取值，并带有注释说明必须与之保持一致。

**唯一刻意的差异轴是等级。** 工具调用的动词用 `label-primary`；推理行的动词用 `label-secondary`。思考是环境性的，调用是事件性的，因此一个长回合里三十多个推理行会退到真正做了工作的调用之后，同时仍然可读。两行在其他一切方面完全相同——过去用来区分它们的 14px/13px 与 24px/22px 差异，是两份拷贝在漂移，而不是两个决定。

运行状态在每一行都变为那条移动的 1px 强调色细线，补齐了视觉世界早已声称的内容。`packages/client` 现在包含零条 `width: 300px` 规则。

折叠运行的摘要精确重复该行的前置槽位——同样的 20px 槽位与 8px 间距——因此它的标签落在它所替代的那些行标题的算术轴上。这条对齐横跨两个包，所以有一个测试读取两份样式表并断言该算术关系（`-margin + padding + icon + gap == tile + gap`）：jsdom 没有布局，而只改动任意一侧都会静默地把每个折叠标签从周围正文旁挪开一步。

为使对话记录自身的页脚保持稳妥，另需两处配套修复。回合的过程控制通过助手操作行既有的 `extraActions` 座位进入该行，而不是自建一个外层容器：新增 flex 容器会使该行从被拉伸的子元素变为按内容定宽，其尾部的耗时标签随之失去收缩能力，页脚便会溢出对话列。而该标签——这一行唯一可收缩的部分——现在改为省略号截断，而不再把整行撑到内容宽度。改动之前，该行的内容在 900px 视口下只是勉强放得下，因此任何新增控件都会把耗时统计挤出列外；现在该行会吸收更窄的列，而不是溢出。

## Alternatives considered

**在每一行放一个 chevron 而不是方块。** 已否决：这会让本来就每行一个的展开提示数量翻倍，而 chevron 列是树形控件的语汇，不是报告的语汇。

**每行使用卡片或填充 chip。** 已否决：这会把第二种外壳塞进一个除输入框外别无控件的对话记录，并让四十行的回合读作四十个堆叠的盒子。

**用竖线或缩进对一组行进行分组。** 已否决：它陈述了折叠早已陈述的分组，而且任何高于发丝线权重的 1px 彩色边缘，都是这个世界并不拥有的一种戏服。

**保留七份拷贝并在原处修正取值。** 已否决：漂移本身就是缺陷。同一个行的四种写法，正是一个 1.98:1 的圆点得以在一次已经宣布废弃该处理的重设计之后存活下来的原因。

## Consequences

在运行中的应用里、1440px 与 900px 两种宽度、两套主题下，对真实会话实测：行为 24px，方块为 20×20 且取 6px 圆角，动词为 `label-primary` 的 13px/500，说明文字为 `label-tertiary` 的 13px/400，**零个**分隔符残留，两种宽度下均无水平溢出。跨全部五种类型实测的 45 行落在同一条标题轴上（28px）。两套主题的对比度均通过 AA：方块字形浅色 5.93:1、深色 5.64:1，说明文字浅色 4.95:1、深色 6.01:1。

`test:gui` 为 4079 通过，仅剩 `ui-brand-official` 那个在干净的 `main` 上同样失败的既有故障。设计检测器对九份被改动的样式表报告零项发现。跨文件轴测试已通过把共享间距从 8px 改为 6px 并观察到预期失败，验证了它确实会拒绝漂移。

仍有两行手写外壳而非组合该原子——`bash-sample` 与 `SkillRow`——因为各自拥有该原子的 props 未能表达的展开交互。它们是残留的漂移风险，而长期的修法是让 `DisclosureRow` 学会该交互，而不是继续重复它的取值。
